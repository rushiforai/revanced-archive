# 調査知見

- Manager登録用のraw URLは既定ブランチ直下の `patches.json` を読む。release workflowの最後で、最新リリースのJSONだけを同ブランチへ同期する。旧リリース再実行は更新対象外で、JSONの版と現在のblob SHAを検証するため、URLだけを変更してJSON配置・同期を省略しない。

- JUnit Jupiterとlauncherは同時更新する。通常taskだけでは未実行configurationのlockが古いまま残るため、追加lock解決taskも実行し、3 lockfileを監査する。
- 難読化名やversion番号をfingerprintに使わず、引数型・戻り型・呼出し命令・`onMeasure/onLayout` などの構造を複数世代で照合する。別patchが先にmethodを可変化した場合は元descriptorでなく可変実装からlabelを取る。
- ReVanced CLIは個別patch失敗でも成果物を保存しexit 0になることがある。APKの存在や終了codeでなく、対象patchの `succeeded` logとpatch後DEXを確認する。
- CLI一時directory内の元APK同名fileはpatch中に変化する。次の互換性試験へ流用せず、Git管理外に保存した各世代の原本から毎回base APKを取り出す。
- XAPKのbaseだけをpatchしても `INSTALL_FAILED_MISSING_SPLIT` になり得る。全module統合後にpatchするか、全splitが同じ署名で揃うことを確認する。Managerのpatch成功とinstall成功を分ける。
- ニコニコのHTMLで最初の `count.like` は対象動画とは限らない。snapshot APIをcontentIdで絞り、返却IDも照合する。値は日次更新でリアルタイムではない。
- 投稿retryは通信callback解放後の最終 `IOException` 派生経路へ接続する。実掲示板へ送らず、ローカル模擬板と `adb reverse` で返信・新規threadを確認する。
- 高度NGは判定method入口でレスと判定器をbridge stackへ保存し、早期returnを含む全returnでpopする。終端のparameter registerは別用途へ再利用され得る。透明NGは対象レスのRecyclerView行だけを0/GONEにし、再利用viewでは必ず復元する。
- 4chan、ふたば、jschanはAPI・投稿form・encodingが別。独立engineとして扱い、4channel URLは実機SSL不具合時に4chanへ正規化しても読取API `a.4cdn.org` との役割を混同しない。
- ローカル/Actionsの同版RVPはmanifest Timestampに加え、Windows/Linux間のD8が生成するlambda・nest accessor番号の差で拡張DEXのSHAも一致しない場合がある。公開前はZIP entry、patch class、拡張DEXのクラス・method・文字列と逆コンパイル後の処理を比較し、公開後はrelease RVPと同梱checksumを照合する。
- 広告通信の完全遮断はbytecode適用だけで断定せず、対象APK・実機のpacket観測で判定する。native/独自暗号/新SDK/Compose移行は追加調査対象。
- 0.8.10.246 devの設定は空`PreferenceScreen`ではなくCompose化されている。設定入口は旧版のXML Preferenceと、新版の`SettingActivity.onCreate`後に既存contentを包む経路の両方へ接続する。
- 画像掲示板をChMate標準画面で扱うには、元サイト別APIを直接ChMate内部modelへ増設するより、loopback限定の`BBSMENU`・`subject.txt`・`dat`変換とURL解析入口の書換えが版差に強い。任意HTTPS URLをjschan扱いせず、jschanは掲示板設定で登録済みのhost/boardだけを書き換える。
- ホーム更新の実体は新版の`AutoCheckWork`、旧版の`ReloadBookmarkTask2`にある逐次処理である。元methodを再帰防止付きで最大4分割すると、難読化された取得・DB・error処理を複製せず並列化できる。
- Android版Managerのapktoolは、246 devの難読化binary XMLで属性値または属性名をnullとして返す場合がある。値は型とraw dataから復元し、名前を復元できない属性だけを除外して不正な`android:`属性を作らない。
- Manager 2.6.0の246 dev復号結果には、10進／16進のframework resource・attr ID、数値のanimation enum、1桁color、数値化されたapp attr名が残る。`public.xml`と既知framework IDへ戻し、未知値は有効な`@0x...`／`?0x...`形式を維持する。attr名は大文字小文字を変えずに復元する。
- 246 devのroot配置binary XMLは属性名のstring pool indexが`-1`でもresource IDを保持する。apktool 2.10系の`AXmlResourceParser.getAttributeName`はこの場合にresource ID解決前に空文字を返すため、`getAttributeNameResource`とAndroid実行時の`android.R.attr`で補完しないとPreferenceの`key`・`entries`・`defaultValue`が全消失し、アプリ起動時に`IntListPreference`がNPEになる。文字列値もprivate string blockから復元し、framework enum・flag・resource参照はAAPT2が受理するsymbolへ戻す。
- 246 devの`RoidonApp.onCreate`にも、同じ結果arrayから2値を読み出して不一致時にnullをthrowするintegrity分岐がある。新版obfuscatorではpaired read間のregister準備が増えるため、短い後方windowだけでは検出できず起動直後にNPEとなる。
- Android 17ではManager 2.6.0の別patcher processの`user.home`が`/`となり、apktool 2.10系が`/.local/share/apktool/framework`を属性解決のたびに作成しようとして失敗する。大量logがBinder bufferを超えると`RemoteFailureException`になるため、RVP内で`java.io.tmpdir/framework`へ明示的に切り替える。
- 246 devの`ResListActivity.onStart`／`onResume`には、内部counterや端末値でnull throw・算術例外・不正配列操作へ分岐するintegrity trapがあり、同じスレッドでも約1/2で終了する。成功経路はsuperの同名ライフサイクル呼び出しだけなので、板一覧Activityと同様に先頭からsuperへ委譲してreturnする。
- 246 devの`WebViewActivity.onStart`にも同型のintegrity trapがあり、ホームの「スレ検索」を開く実機UI回帰検査でNPEを再現した。ライフサイクルtrapの対象は板一覧・レス一覧・WebViewの3 Activityとして回帰testで固定する。
- 246 devの`ResEditActivity.onStart`にも同型のintegrity trapがあり、スレッドtoolbarの「書き込む」から返信ダイアログを開く検査でArithmeticExceptionを再現した。ライフサイクルtrapの対象は板一覧・レス一覧・書き込み・WebViewの4 Activityとして回帰testで固定する。
- 246 devのActivityを横断すると、Home・Search・ThreadListにもthrow／divideを使うライフサイクルtrapがある。旧版へ無条件適用せず、対象7 Activityの`onStart`／`onResume`／`onPause`でsuper同名呼出しとtrap opcodeが共存するmethodだけを置換する。
- `ResEditActivity.onResume`のtrapはthrow／divideではなく負数を長さにした`NEW_ARRAY`で終了する。ライフサイクルの構造判定では`NEW_ARRAY`もtrap候補とし、super同名呼出しとの共存を必須にする。
- 246 devの画像関連は`ImagesViewer2Activity`と`ImageListActivity`にも同型trapがある。後者の`onStart`／`onPause`は同classのstatic dispatcherへ処理を委譲するため、入口だけのopcode走査では見落とす。同class呼出しだけを訪問済み集合付きでたどり、super同名呼出しとtrapの共存を判定する。両画像Activityの`attachBaseContext(Context)`も正常経路がsuperへの委譲だけであることを元DEXの逆コンパイルで確認した（2026-11-04、`IntegrityCheckPatch.kt`）。
- 246 devのCompose画面はXMLの`toolbarContentTop`を使わず、ChMateのFrameLayout派生広告ViewをAndroidViewへ載せる。広告Viewには`setBannerAdRequest %s`／`createAdView2 request=%s`の2リテラルがあり、50dpの最小高と下paddingを持つ。SDK子Viewだけを消しても親の高さが残るため、両リテラルとAndroid基底classで生成元を検出し、constructorの正常return直前でpadding・最小高・layout高・visibilityを折りたたみ、SDK・自社宣伝のfactoryも止める（2026-11-04、`NativeAdViewPatch.kt`）。
- sportschanの`/librejp/catalog.json`と`/librejp/thread/16592.json`は2026-11-04にHTTP 200のjschan JSONを返した。jschanの明示的な`/板/thread/番号.html`は未登録でも変換する一方、任意のHTTPSページを板扱いしない。直接URLからの板登録では、一時mapへ入れる前に保存する必要がある。短いremote thread IDをChMate用に変換した対応表はprocessを越えて保持しないと、catalogから消えたスレッドを再起動後に再解決できない（`ImageBoardIntegration.java`／`ImageBoardProxyServer.java`）。
- ローカルの検証環境はJDK 17、Android SDK、公式ReVanced CLI 6.0.0、Manager 2.6.0を使う。補助JARとOSV-ScannerはGit管理外の`output/tools/`、端末証跡・互換性検査は`output/qa/`へ保存する。GradleはGitHub Packagesの読取資格情報を環境変数で渡す。`settings-gradle.lockfile`はOSVの自動判定名でないため、一時directoryの`gradle.lockfile`へcopyして検査する。現時点の同fileはpackage 0件、残り2 lockfileは68／170 packageである（2026-11-04）。
- ChMateの「URLを開く」はContext付きwrapperを経由せず、URIをparseするstatic synthetic methodを直接呼ぶ場合がある。246 devのcore parserは引数が`(Companion, String)`で、旧版の`(String)`だけを探しても見つからない。さらに`Uri.getHost()`から再構築すると内部URLのportが落ち、HTTPSへ正規化されるため、`127.0.0.1`かつ画像掲示板tokenのpathだけを`BBSUrlInfo`のURL生成時にHTTP・固定portへ戻す。通常URLやローカル模擬板には適用しない（2026-11-04実機のsportschan検査、`DeepIntegrationPatch.kt`／`ImageBoardIntegration.java`）。
- AQUOS / Android 16 / Manager 2.6.0で、公開v1.2.4とローカルv1.2.5を同時登録すると、候補の拡張DEXに旧版のpatch本体を組み合わせたAPKを生成した。選択1 patch・準備/適用/保存各2/2や、Managerの再起動だけでは検出・解消できなかった。公開版のChMateソースを一時除去してManagerをforce-stopし、候補だけで再適用すると、core URL parserのフック、native広告Viewのconstructor/factory修正、画像Activityのsuper委譲がすべてCLI生成物と一致した。検査ではpatch後DEXを照合し、公開後は候補ソースを除去して固定URLを戻す（2026-11-04、`output/qa/issue16/`のGit管理外証跡）。
- 246 devは外部板をHTTPS優先で試す。`external_board_scheme_cache`を持つclassの`(String host, String url) -> boolean`判定が有効だと、HTTP専用のloopback proxyへTLSを試し、本文が表示されない。URL getterだけを直しても解消しない。画像掲示板用のloopback URLだけをこの判定から外すと、実機でDATのGET・HTTP 200とsportschanの141レス表示を確認できた。一般サイトのHTTPS優先とscheme cacheは維持する。診断用の一時ログは製品から除去する（2026-11-04、`DeepIntegrationPatch.kt`）。
- Compose設定の部分表示カードは、説明文のタップでもスイッチが切り替わる。画面端の説明文だけで画面遷移を推定せず、カード全体と実スイッチが見える位置で操作し、検査前後の状態を照合する。NG編集では全tab・操作種類・追加/編集の取消を検査し、既存のNGデータ全行の走査と画面検査を混同しない（2026-11-04、AQUOS実機UI検査）。
- ChMateの外部`ACTION_VIEW` filterは既知hostのHTTPS URLに限られ、loopback URLをpackage指定だけで渡すと`ActivityNotFoundException`になる。板を開くときは`ThreadListActivity`を明示し、Intentのdataへ板URLを渡す。`bidString`だけではBBSMENU未更新の板をDBで解決できない。processが生存していてもActivityが終了して設定へ戻る場合があるため、UI検査では遷移先Activityと実表示内容も照合する（2026-11-04、`ImageBoardSourcesActivity.java`／元のThreadListViewModel）。
