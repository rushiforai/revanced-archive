00 What we are building

Two subtitle lines on screen at once while a video plays. The top line is the language you are learning, the way the speaker said it. The bottom line is the same sentence in German. Everything below is the machinery needed to put that second line on the screen of an app we do not have the source code to.

The rest of this page is the pipeline, in the order we walk it: get the app, read the app, find the exact spot to change, change it, run it, watch it.

01 Getting the app

An APK is a ZIP file. That is the whole trick to opening it.

Android ships apps as APK files, and an APK is a ZIP archive with a fixed layout: compiled code, compiled resources, a manifest, and assets. Google no longer ships YouTube as one file. It ships an app bundle, which the Play Store splits per device, so the phone holds several pieces:

File on the phoneWhat is in it
base.apkAll the Java/Kotlin code and the shared resources. 54 MB. This is the one we patch.
split_config.arm64_v8a.apkNative libraries compiled for the phone's CPU.
split_config.xxhdpi.apkImages at the phone's screen density.
split_config.en.apkEnglish strings.

The phone carries both a stock and a patched YouTube, side by side, because a patched build gets its own package name and cannot overwrite the original:

app.revanced.android.youtube    20.40.45   enabled    ← the patched one, in use
com.google.android.youtube      20.46.37   disabled   ← stock, kept but switched off
app.revanced.android.gms        0.3.13.2   enabled    ← microG, so it can sign in

Pulling either one off the phone is a two-step affair, and it is the most honest source there is: it is exactly the binary that runs.

# where Android keeps the installed pieces
adb shell pm path com.google.android.youtube
adb pull /data/app/~~7WXU.../base.apk yt-20.46.37-base.apk

For patching we need a stock build of the exact version ReVanced supports, so that one comes from APKMirror instead. Whatever the source, the first thing to do is check who signed it — a genuine build carries Google's certificate, and the same fingerprint appears on the app that came off the phone:

apksigner verify --print-certs yt-20.40.45-base.apk
  certificate DN: CN=Android, O=Google Inc., L=Mountain View
  SHA-256 digest: 5aad2bee6db95d17e05a08d7d1e64c10a1511879154483916b6ae6c7fd9cb0c6

02 Turning the app back into code

Three tools, three different levels of "readable".

A .dex file is Dalvik bytecode: the instructions Android's runtime executes, not the Java that was written. Nobody reads dex directly. We convert it twice over, because the two results are good at different things.

jadx: dex back to Java

jadx guesses the Java that would compile to this bytecode. It is the version you read to understand what a method does. It is a reconstruction, so it can be wrong in the details, and it will not always compile.

baksmali (inside apktool): dex to smali

Smali is a text form of the bytecode itself, one line per instruction, registers and all. Ugly, exact, and reversible: you can edit smali and assemble it back into a working dex. Every ReVanced patch is ultimately an edit at this level.

It reads better than "assembly" suggests. This is a whole method, copied out of 20.40.45:

.method public final y()Z
    const-string v0, "DISABLE_CAPTIONS_OPTION"
    invoke-virtual {p0}, …/SubtitleTrack;->g()Ljava/lang/String;
    move-result-object v1
    invoke-virtual {v0, v1}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
    move-result v0
    return v0
.end method

Which is nothing more than:

public final boolean y() {
    return "DISABLE_CAPTIONS_OPTION".equals(g());
}

The vocabulary is small. p0…pN are the parameters, and in an instance method p0 is this; v0…vN are locals; types are single letters, Z for boolean, I for int, V for void, L…; for an object. A call's return value lands in a hidden slot, which is why every invoke is followed by a move-result. Unlike JVM bytecode, which pushes and pops a stack, Dalvik is register-based: each instruction names the registers it touches.

Keep that method in mind — it is the one the next two sections take apart.

apktool: the resources

Layouts and strings are compiled too. apktool turns resources.arsc and the binary XML back into readable XML, which is how a patch can add a view to the player's layout, or read the numeric id behind a name like youtube_controls_bottom_ui_container.

03 Why the code looks like nonsense

Class pc, method a, field b. On purpose.

Google runs the app through R8, which shrinks and obfuscates: every class, method and field that is not part of a public interface gets renamed to something short and meaningless. It makes the download smaller and the app harder to read, and both are the point. There is no mapping file for us.

So a name is worthless to us, and worse than worthless across versions: the names are reassigned on every release. A patch that says "call into class pc" works for exactly one build of the app and silently targets something else in the next.

Three things do survive obfuscation, and they are what everything else is built on:

  • String literals. A method that logs "DISABLE_CAPTIONS_OPTION" still contains that text after obfuscation. Strings are data, not names.
  • Resource names. accessibility_captions_button_name lives in the resource table and the code refers to it by a stable numeric id.
  • Shape. The instruction sequence, the return type, the parameter types, whether the method is public and final. Renaming does not change what the code does.

04 Fingerprints: finding a method without knowing its name

Describe the method well enough that only one in the whole app matches.

This is ReVanced's central idea. Instead of naming a target, a patch describes it, and the patcher searches all 45 MB of bytecode for the one method that fits. Here is a real one from the existing "Disable auto captions" patch:

internal val BytecodePatchContext.subtitleTrackMethod
    by gettingFirstMethodDeclaratively("DISABLE_CAPTIONS_OPTION") {
    accessFlags(AccessFlags.PUBLIC, AccessFlags.FINAL)
    returnType("Z")          // returns a boolean
    parameterTypes()          // takes no arguments
}

Read it as a sentence: the public final method that takes nothing, returns a boolean, and mentions the string DISABLE_CAPTIONS_OPTION. That description survives the app being rebuilt and renamed, which is why ReVanced can support six YouTube versions from one source tree.

When a fingerprint stops matching after a YouTube update, that is the maintenance work: open the new version in jadx, find where the string moved, and widen or correct the description.

04b What the real app looks like inside

Disassembled 45 MB of YouTube 20.46.37 and went looking for the subtitle machinery.

Obfuscation is not uniform. Library code that has to keep working through reflection, serialization or the Android framework keeps its class name, while its methods are renamed anyway. The subtitle model is exactly that case:

// class name intact, every method renamed to a single letter
com/google/android/libraries/youtube/player/subtitles/model/SubtitleTrack
    public abstract a() : String     public abstract p() : boolean
    public abstract b() : int        public abstract q() : boolean
    …                                public static  s(String) : SubtitleTrack

com/google/android/libraries/youtube/player/subtitles/ui/SubtitleWindowView
    // the view that draws the caption box on screen

And the caption plumbing is all there, under short names:

What it isGives it awayIn 20.40.45In 20.46.37
Builds the URL for a translated caption track"&tlang=", "AUTO_TRANSLATE_CAPTIONS_OPTION"amclamhn
Parses the srv3 caption format"/timedtext/body/p"aigvakgi
One caption track: language, name, flags"DISABLE_CAPTIONS_OPTION"SubtitleTrack, moved classes2 → classes5

The drift is uneven, and that is the interesting part. Both classes that changed internally were also renamed, and SubtitleTrack moved to a different dex file — while inside it, y() is byte-for-byte identical in both builds, string constant and all. R8's naming is stable as long as the code feeding it barely changes, so names survive in the quiet corners and move exactly where the code moved.

Which is worse than uniform chaos. A patch pinned to names would keep working on the untouched methods and silently point at the wrong code on the changed ones. Matching on strings and shape avoids having to know which case you are in.

Two things follow. First, the app already fetches and translates captions through the same endpoint we tested from the laptop, which is a good sign for the approach. Second, it does all of that for exactly one track at a time, and the entire pipeline from track selection to the view assumes one. That is why the plan draws our own overlay instead of trying to make YouTube's renderer show two.

05 What a patch actually is

A small edit at patch time, and a normal Java class doing the real work at runtime.

A ReVanced patch has two halves, and confusing them is the main source of confusion when reading the repository.

  • The patch is Kotlin that runs on this laptop, once, while building the modified APK. It finds methods by fingerprint and splices instructions into them.
  • The extension is plain Java that gets compiled into a dex and merged into the APK. It runs on the phone, inside YouTube, with all the normal Android APIs available. Our subtitle logic lives here.

The bytecode the patch inserts is almost always the same shape: a single call out to the extension. This is the real insertion from the auto-captions patch, in smali:

invoke-static {}, Lapp/revanced/extension/youtube/patches/DisableAutoCaptionsPatch;->disableAutoCaptions()Z
move-result v0
if-eqz v0, :auto_captions_enabled
const/4 v0, 0x1
return v0
:auto_captions_enabled
nop

In words: at the top of YouTube's own method, ask our class a question; if it says yes, return early with true; otherwise fall through into YouTube's original code, untouched. Every hook we write for dual subtitles is that pattern — hand a value to our code, or let our code decide.

06 Where the two lines come from

YouTube already has both, including the translation. It just doesn't show them together.

This was the open question, and it is now answered by experiment. YouTube's own app fetches captions from an internal API called InnerTube. We can call it the same way, from inside the patched app, with no login:

  • Ask /youtubei/v1/player for a video id as the Android client. Back comes the list of caption tracks, each with a signed URL, plus the list of languages YouTube is willing to translate into.
  • Fetch a track as json3: every cue with a start time, a duration, and per-word timings inside it.
  • Fetch the same track again with &tlang=de: YouTube's own translation. The first attempts answer 429 Too Many Requests; retried, it turns into a 200 with real German, and then stays instant. On a fresh video that was five refusals over about forty seconds, then success.
  • The translated track comes back index-aligned with the original: same number of cues, identical start times. Pairing line one with line two is a zip over two arrays.

That removes an entire subsystem from the plan. No translation service, no API key, no on-device model.

One wrinkle worth knowing about: the position hook fires only once per second, which is far too coarse for subtitles. Between ticks we advance our own clock by the wall clock times the playback speed, and resync on every tick, every seek and every pause.

07 Which version, and why it matters

A patch is written against one build of the app, not against "YouTube".

ReVanced declares compatibility with six builds: 20.14.43, 20.21.37, 20.26.46, 20.31.42, 20.37.48 and 20.40.45. We take 20.40.45, the newest of them, which is also the build already patched and running on the phone. Its stock APK is 169 MB, carries Google's signature, and ships all four CPU architectures including x86_64 — so it installs on the emulator without any ARM translation.

How far behind is that? Here is the whole supported set with the day each build shipped:

So the newest build ReVanced supports is about ten months old, and the six versions were all added to the repository on one day, 7 February 2026, with nothing added since — even though the development branch is still getting commits, the most recent four days ago. The gap is softer than it looks, because the patch source already contains explicit handling for 21.02 through 21.08, but those versions are not declared supported. Carrying the patch forward to a 21.x build is work we would be doing ourselves.

The practical consequence for anyone running a patched build: automatic updates have to stay off. The patched app has its own package name (app.revanced.android.youtube), so it sits beside the stock one rather than replacing it, and the stock one gets disabled.

08 The loop, once code exists

Edit, build, patch, install, watch the log. Minutes, not seconds.

# 1. build our patch bundle
./gradlew :patches:buildAndroid

# 2. apply it to the stock APK and install on the emulator
java -jar revanced-cli-6.0.0-all.jar patch \
  -p patches.rvp --exclusive -e "Dual subtitles" \
  -i emulator-5554 yt-20.40.45.apk -o yt-patched.apk

# 3. watch our own logging
adb logcat | grep revanced

Testing happens on the emulator, not the phone. The local x86_64 images translate ARM code, so the ARM-only YouTube build installs and runs there — verified: the emulator reports x86_64,arm64-v8a and ships the translation library. The phone gets the finished APK.

Because that loop costs minutes, as much logic as possible gets built and tested outside the patched app first, in a throwaway app where a rebuild is seconds.

08b Making an obfuscated method callable

When the name changes every release, derive it instead of writing it down.

Styling YouTube's own captions means calling setters on its caption view. The view keeps its class name, being library code, but its setters are called a, b, c, d and e, and nothing says which does what. Worse, those letters are reassigned when the app is rebuilt, so writing today's answer into the patch guarantees a wrong call later.

The app answers the question itself. It applies caption styles from an object that mirrors Android's own CaptionStyle, and the method that does it loads one field and passes it straight to one setter:

iget v0, v0, Lamcv;->e:I               // foregroundColor
invoke-virtual {p1, v0}, …SubtitleWindowView;->d(I)V

iget v0, v0, Lamcv;->a:I               // backgroundColor
invoke-virtual {p1, v0}, …SubtitleWindowView;->c(I)V

So the patch walks that method, notes which style field was loaded before each call, and comes out with the mapping. Then it adds a method to the view with a name of its own choosing, which cannot drift because we picked it:

.method public final patch_applyCaptionStyle(IIIIF)V
    invoke-virtual { p0, p1 }, …->d(I)V      // text colour
    invoke-virtual { p0, p2 }, …->c(I)V      // background
    invoke-virtual { p0, p3 }, …->a(I)V      // edge colour
    invoke-virtual { p0, p4 }, …->b(I)V      // edge type
    invoke-virtual { p0, p5 }, …->e(F)V      // text scale
    return-void
.end method

The extension then calls patch_applyCaptionStyle by name. The generated bytecode was checked against the mapping worked out by hand from the disassembly, and the two agree.

10 What the loop actually costs

Two minutes from edit to running app, and where they go.

StepTimeWhy
Gradle, extension changed26–32 sRecompiles one module; the first build was 2 min 51 s
Applying the patches~75 sRecompiles eight dex files and the resources of a 170 MB app, then signs it
Installing12–15 sPushing the rebuilt APK

The patch step dominates and does not shrink: reusing the CLI's temporary directory made it slower, not faster (98 s against 75 s), and cutting the number of patches barely moved it. What does help is not going around the loop at all — keeping the logic testable outside the patched app, and making behaviour a setting so tuning it needs no rebuild.

Debugging inside the app is ordinary Android work once the debugging patch is included: turn on Debug logging in ReVanced settings, then read adb logcat | grep revanced. That is how the player button was tracked down — it logged that it initialised and became visible while apparently not being on screen, and a log of its measured bounds showed it had been there all along, at 828,450 to 954,608, which is exactly the icon that had been mistaken for one of YouTube's own.
